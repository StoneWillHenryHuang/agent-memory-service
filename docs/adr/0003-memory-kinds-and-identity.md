# ADR 0003: Versioned Identity Strategies for Memory Kinds

- Status: Accepted
- Date: 2026-07-30

## Context

Summary, fact, and profile memories have different cardinality and update behavior. A single database uniqueness rule cannot express all three safely, and random IDs alone do not provide deterministic replay behavior.

Record identity and command idempotency solve different problems and must not be conflated.

## Decision

### Storage identity

The authoritative identity of a memory is:

```text
(tenant_id, subject_id, namespace, memory_id)
```

All deterministic IDs are generated by a versioned `IdentityStrategy`. The default generator canonicalizes an array of typed identity components as UTF-8 JSON, normalizes configured text components with Unicode NFC, hashes the bytes with SHA-256, and adds a kind prefix plus identity-schema version.

Exact serialization and prefix values will be covered by public golden tests before v0.1 is released. Changing canonicalization or digest construction creates a new identity-schema version; an already published version is never silently changed.

### Summary identity

The default summary natural key is:

```text
(scope, session_id, summary_strategy_version)
```

The default strategy requires a non-empty session ID and produces one logical summary per key. A new event updates that record through compare-and-swap.

### Fact identity

Facts are multi-valued. For an add action, the default fact natural key is:

```text
(scope, canonical_fact_content, fact_identity_version)
```

Canonical fact content uses a deliberately narrow, versioned normalization; it does not claim semantic equivalence. An update or delete action must target an existing fact ID. Similarity search cannot select a mutation target by itself.

Updates preserve the target ID. If an update would canonicalize to another existing fact, the strategy returns an explicit merge/conflict decision rather than silently overwriting either record.

### Profile identity

The default profile natural key is:

```text
(scope, profile_name, profile_strategy_version)
```

`profile_name` defaults to `default`. The profile is updated through compare-and-swap and event-time freshness checks.

### Custom kinds

Custom memory kinds are namespaced strings with an injected identity strategy. An adapter stores them without assuming only the default three kinds exist. A custom strategy must declare its natural key, cardinality, identity version, and update semantics.

### Command idempotency

Every mutating command also has a scoped idempotency key and canonical payload digest. The command key prevents duplicate application; it is not used as the record ID.

## Consequences

- Repeated extraction of the same default logical target converges on a stable ID.
- Identity behavior is reproducible across adapters and test runs.
- Changing normalization requires a migration or coexistence plan.
- Hash-derived IDs hide raw identity components but are not treated as encryption or authorization.
- Applications that need semantic fact merging must supply an explicit strategy.

## Rejected alternatives

### Random IDs for every extracted value

Rejected because retries and replays would create uncontrolled duplicates without a separate deduplication index.

### One uniqueness rule for every kind

Rejected because summary/profile are singleton-like while facts are intentionally multi-valued.

### Use embedding similarity as fact identity

Rejected because similarity is model-dependent, non-deterministic across model changes, and unsafe as an implicit mutation selector.
